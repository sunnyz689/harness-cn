## 1. Description 编写模式

Description 是技能唯一的触发机制。Claude 只能看到 `available_skills` 列表中的 name + description，并据此决定是否使用该技能。

### 理解触发机制

Claude 对于能用基础工具轻易处理的简单任务，往往不会调用技能。像"帮我读一下这个 PDF"这样的简单请求，即便 description 写得完美也可能不触发。越是复杂、多阶段且专业的工作，技能被触发的概率越高。

### 编写原则

1. 同时描述**技能做什么**与**具体的触发场景**
2. 明确边界条件，区分相似但不应触发的情况
3. 写得稍微"急切"一些 —— Claude 在触发判断上偏保守，需要适当补偿

### 正例

```yaml
description: "PDF 파일 읽기, 텍스트/테이블 추출, 병합, 분할, 회전, 워터마크,
  암호화/복호화, OCR 등 모든 PDF 작업을 수행. .pdf 파일을 언급하거나
  PDF 산출물을 요청하면 반드시 이 스킬을 사용할 것. 단순히 PDF를
  '읽어달라'는 요청이 아닌 변환/편집/분석이 필요할 때 특히 유용."
```

```yaml
description: "엑셀/CSV/TSV 파일의 열 추가, 수식 계산, 서식, 차트,
  데이터 정제를 포함한 모든 스프레드시트 작업. 사용자가 스프레드시트
  파일을 언급하면 — 심지어 캐주얼하게('다운로드 폴더의 xlsx')라고만
  해도 — 이 스킬을 사용할 것."
```

### 反例

- "处理数据的技能" —— 过于模糊，未指明是哪些文件/操作
- "PDF 相关工作" —— 没有列出具体动作，未描述触发场景

## 2. 正文编写风格

### Why-First 原则

LLM 一旦理解了原因，即便在边缘场景下也能正确判断。传递上下文比强硬规则更有效。

**反例：**
```markdown
ALWAYS use pdfplumber for table extraction. NEVER use PyPDF2 for tables.
```

**正例：**
```markdown
테이블 추출에는 pdfplumber를 사용한다. PyPDF2는 텍스트 추출에 특화되어
있어 테이블의 행/열 구조를 보존하지 못하기 때문이다. pdfplumber는
셀 경계를 인식하여 구조화된 데이터를 반환한다.
```

### 一般化原则

一旦在反馈或测试结果中发现问题，不要做只针对特定示例的狭隘修改，而要在**原理层面进行一般化**。

**过拟合式修改：**
```markdown
"Q4 매출" 열이 있으면 해당 열을 숫자로 변환하라.
```

**一般化后的修改：**
```markdown
열 이름에 "매출", "금액", "수량" 등 수치를 암시하는 키워드가 있으면
해당 열을 숫자 타입으로 변환한다. 변환 실패 시 원본 값을 유지한다.
```

### 命令式语气

用"读取"、"生成"等直接动词起头，避免"可以读取"、"请生成"之类委婉或可商量的语气。技能就是指令书。

### 节省上下文

上下文窗口是公共资源。逐句自问：这一句是否值得消耗 token：
- "Claude 已经知道的内容吗？" → 删除
- "没有这段说明 Claude 会出错吗？" → 保留
- "一个具体示例比长篇说明更有效吗？" → 用示例替代

## 3. 输出格式定义模式

在产物格式很重要的技能中使用：

```markdown
## 보고서 구조
다음 템플릿을 정확히 따른다:

# [제목]
## 요약
## 핵심 발견
## 권장 사항
```

格式定义应简洁，加上真实示例会更有效。

## 4. 示例编写模式

示例比冗长的描述更有效：

```markdown
## 커밋 메시지 형식

**예시 1:**
입력: JWT 토큰 기반 사용자 인증 추가
출력: feat(auth): JWT 기반 인증 구현

**예시 2:**
입력: 로그인 페이지에서 비밀번호 표시 버튼이 동작하지 않는 버그 수정
출력: fix(login): 비밀번호 표시 토글 버튼 동작 수정
```

## 5. Progressive Disclosure 模式

### 模式 1：按领域拆分

```
bigquery-skill/
├── SKILL.md (개요 + 도메인 선택 가이드)
└── references/
    ├── finance.md (매출, 빌링 메트릭)
    ├── sales.md (기회, 파이프라인)
    └── product.md (API 사용량, 기능)
```

用户问营收时，只加载 finance.md。

### 模式 2：按需展开

```markdown
# DOCX 처리

## 문서 생성
docx-js로 새 문서를 생성한다. → [DOCX-JS.md](references/docx-js.md) 참조.

## 문서 편집
단순 편집은 XML을 직접 수정.
**추적 변경이 필요하면**: [REDLINING.md](references/redlining.md) 참조
```

### 模式 3：大型参考文件的结构

300 行以上的 reference 文件应在顶部加上目录：

```markdown
# API 레퍼런스

## 목차
1. [인증](#인증)
2. [엔드포인트 목록](#엔드포인트-목록)
3. [에러 코드](#에러-코드)
4. [레이트 리밋](#레이트-리밋)

---

## 인증
...
```

## 6. 脚本打包判断标准

观察测试执行中各智能体的转录。出现以下模式时，即为打包候选：

| 信号 | 处置 |
|------|------|
| 3 次测试 3 次都生成了同样的辅助脚本 | 打包到 `scripts/` |
| 每次都执行相同的 pip install/npm install | 在技能中明确依赖安装步骤 |
| 反复使用同一套多阶段方法 | 在技能正文中写成标准流程 |
| 每次都遇到类似错误并应用同样的规避办法 | 在技能中写入已知问题与解决方法 |

打包好的脚本必须经过执行测试。

## 7. 数据 schema 标准

为技能间数据交换的一致性，采用统一 schema。可用于在 Harness 中生成技能的测试/评估。

### eval_metadata.json

每个测试用例的元数据：

```json
{
  "eval_id": 0,
  "eval_name": "descriptive-name-here",
  "prompt": "사용자의 작업 프롬프트",
  "assertions": [
    "산출물에 X가 포함되어 있다",
    "Y 형식으로 파일이 생성되었다"
  ]
}
```

### grading.json

基于断言（assertion）的评分结果：

```json
{
  "expectations": [
    {
      "text": "产物中包含 '北京'",
      "passed": true,
      "evidence": "在第 3 步确认到 '北京 区域数据提取'"
    }
  ],
  "summary": {
    "passed": 2,
    "failed": 1,
    "total": 3,
    "pass_rate": 0.67
  }
}
```

**字段名注意：** 严格使用 `text`、`passed`、`evidence`（禁止使用 `name`/`met`/`details` 等变体）。

### timing.json

执行时间/令牌计量：

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

子智能体完成通知中，要立即保存 `total_tokens` 和 `duration_ms`。该数据仅在通知时刻可访问，之后无法恢复。

## 8. 不应纳入技能的内容

- README.md、CHANGELOG.md、INSTALLATION_GUIDE.md 等附属文档
- 技能生成过程的元信息（测试结果、迭代记录）
- 面向用户的说明文档（技能是给 AI 智能体的指令书）
- Claude 已经掌握的通用知识

## 9. 技能复用设计

创建新技能前，先确认与现有技能是否重复。反复搭建 Harness 时，功能重叠的技能容易以不同名字累积。

| 情况 | 处置 |
|------|------|
| 现有技能已完全包含新增功能 | 不创建新技能 —— 把现有技能挂到智能体上 |
| 现有技能部分覆盖且可一般化 | 一般化现有技能以扩展 |
| 现有技能中本意是领域特化的部分 | 继续创建新技能 —— 作为独立技能保留 |
| 功能范围完全不同 | 继续创建新技能 |

**原则：** 一个技能越专注于一个角色，复用性越高，重复越少。当角色有两个以上时，先考虑是否能拆分。

### 一般化到何种程度

一般化可以无限进行，因此要在**有意设定的责任范围**停下。保留有意的领域特化，只去除偶然的依赖。

例："fintech 风险评估 PDF"技能

| 阶段 | 结果 |
|------|------|
| 去除 fintech 依赖 | "评估结果 PDF" —— 责任范围若是评估报告，就在此停止 |
| 去除评估依赖 | "PDF 格式化" —— 如果已存在则不要新建，直接复用 |

如果责任范围本就刻意限定为"fintech 风险评估"，则不要一般化，作为独立技能保留。

依赖该技能的智能体行为可能会被改变。扩展前先确认依赖关系，并在 description 中反映扩展后的使用范围。
