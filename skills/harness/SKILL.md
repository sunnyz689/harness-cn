# Harness — Agent Team & Skill Architect

针对领域/项目构建 Harness（Harness 工具套件），定义各智能体的角色，并生成智能体所需技能的元技能。

**核心原则：**
1. 生成智能体定义（`.claude/agents/`）与技能（`.claude/skills/`）。
2. **将智能体团队作为默认执行模式。**
3. **在 CLAUDE.md 中注册 Harness 指针。** — 仅记录最小指针（触发规则 + 变更历史），以便新会话中触发编排器技能。
4. **Harness 不是固定物，而是不断演进的系统。** — 每次执行后吸收反馈，持续更新智能体、技能与 CLAUDE.md。

## 工作流

### Phase 0: 现状审计

Harness 技能被触发后，首先确认既有 Harness 的现状。

1. 读取 `项目/.claude/agents/`、`项目/.claude/skills/`、`项目/CLAUDE.md`
2. 根据现状分支选择执行模式：
   - **新建构建**：智能体/技能目录不存在或为空 → 从 Phase 1 起完整执行
   - **既有扩展**：已有 Harness，且收到新增智能体/技能请求 → 按下方 Phase 选择矩阵仅执行必要的 Phase
   - **运维/维护**：对既有 Harness 的审计、修改、同步请求 → 转到 Phase 7-5 运维/维护工作流

   **既有扩展时的 Phase 选择矩阵：**
   | 变更类型 | Phase 1 | Phase 2 | Phase 3 | Phase 4 | Phase 5 | Phase 6 |
   |----------|---------|---------|---------|---------|---------|---------|
   | 新增智能体 | 跳过（沿用 Phase 0 结果） | 仅做编排决策 | 必需（含 3-0） | 如需专用技能则执行（含 4-0） | 修改编排器 | 必需 |
   | 新增/修改技能 | 跳过 | 跳过 | 跳过 | 必需（含 4-0） | 仅在连接变更时 | 必需 |
   | 架构变更 | 跳过 | 必需 | 仅针对受影响的智能体（含 3-0） | 仅针对受影响的技能（含 4-0） | 必需 | 必需 |
3. 比对既有智能体/技能清单与 CLAUDE.md 记录，检测不一致（drift，漂移）
4. 将审计结果汇总向用户报告，并获得执行计划确认

### Phase 1: 领域分析
1. 从用户请求中识别领域/项目
2. 识别核心作业类型（生成、验证、编辑、分析等）
3. 基于 Phase 0 审计结果，分析与既有智能体/技能的冲突/重复
4. 探索项目代码库 — 掌握技术栈、数据模型、关键模块
5. **感知用户熟练度** — 从对话中的上下文线索（使用术语、提问层次）判断技术水平，并据此调节后续沟通语气。对编程经验较少的用户，不在未解释的情况下使用 “assertion”、“JSON schema” 等术语。

### Phase 2: 团队架构设计

#### 2-1. 执行模式选择

**智能体团队是最高优先级的默认值。** 当两名及以上智能体协作时，必须优先评估智能体团队方案。团队成员通过直接通信（SendMessage）与共享任务列表（TaskCreate）自我协调，发现共享、冲突讨论与缺漏补全能提高结果质量。

| 模式 | 何时使用 | 特性 |
|------|----------|------|
| **智能体团队**（默认） | 两人及以上协作、需要实时协调与反馈交换、相互参考中间产物 | `TeamCreate` + `SendMessage` + `TaskCreate` 实现自我协调 |
| **子智能体**（替代） | 单一智能体作业、只需将结果返回主控、团队通信开销过大时 | 直接调用 `Agent` 工具，通过 `run_in_background` 实现并行 |
| **混合** | 各 Phase 特性差异显著时 — 例如：并行采集（子）→ 基于共识的整合（团队） | 按 Phase 粒度混合配置团队/子智能体 |

**决策顺序：**
1. 首先评估能否以智能体团队设计 — 两人及以上即为默认
2. 仅在结构上不需要团队通信（仅传递结果）且团队开销大于收益时选择子智能体
3. 若各 Phase 特性差异明显则考虑混合 — 在编排器中明示每个 Phase 的执行模式

> 详细对比表与按模式划分的决策树参见 `references/agent-design-patterns.md` 的“执行模式”章节。

#### 2-2. 架构模式选择

1. 将作业拆分为专家领域
2. 决定智能体团队结构（架构模式参见 `references/agent-design-patterns.md`）
   - **流水线（Pipeline）**：顺序依赖型作业
   - **扇出/扇入（Fan-out/Fan-in）**：并行独立型作业
   - **专家池（Expert Pool）**：按情境择优调用
   - **生产者-审阅者（Producer-Reviewer）**：先生成后质检
   - **监督者（Supervisor）**：中心智能体管理状态与动态分配
   - **层级委派（Hierarchical Delegation）**：上层智能体向下层递归委派

#### 2-3. 智能体拆分准则

按专业性、并行性、上下文、复用性四个维度判断。详细准则表参见 `references/agent-design-patterns.md` 的“智能体拆分准则”。与既有智能体的重复/复用检讨在 Phase 3-0 中处理。

### Phase 3: 生成智能体定义

#### 3-0. 既有智能体重复检讨

新建智能体前，先检查 `项目/.claude/agents/` 中既有智能体是否重复。反复搭建 Harness 时，角色重叠的智能体容易以不同名字累积。

> 重复分类标准与复用设计参见 `references/agent-design-patterns.md` 的“智能体复用设计”。

**所有智能体必须以 `项目/.claude/agents/{name}.md` 文件形式定义。** 禁止在没有智能体定义文件的情况下，直接把角色塞进 Agent 工具的 prompt 中。理由：
- 智能体定义需以文件存在，下一个会话才可复用
- 团队通信协议需明示，才能保证智能体间协作质量
- Harness 的核心价值是智能体（谁）与技能（怎么做）的分离

即便使用内置类型（`general-purpose`、`Explore`、`Plan`），也要生成智能体定义文件。内置类型通过 Agent 工具的 `subagent_type` 参数指定，而智能体定义文件承载角色、原则与协议。

**模型设置：** 所有智能体均使用 `model: "opus"`。调用 Agent 工具时必须显式声明 `model: "opus"` 参数。Harness 的质量与智能体的推理能力直接相关，opus 能保证最高质量。

**团队重组：** 每个会话仅允许激活一个智能体团队，但可在 Phase 之间解散并重建团队。若像流水线（Pipeline）模式那样每个 Phase 需要不同的专家组合，先将上一团队的产物落盘为文件，再清理团队并创建新团队。

将每个智能体定义到 `项目/.claude/agents/{name}.md`。必备小节：核心角色、作业原则、输入/输出协议、错误处理、协作。在智能体团队模式下需追加 `## 团队通信协议` 小节，明示消息收发对象与作业请求范围。

> 定义模板及完整真实文件参见 `references/agent-design-patterns.md` 的“智能体定义结构” + `references/team-examples.md`。

**包含 QA 智能体时的必备事项：**
- QA 智能体应使用 `general-purpose` 类型（`Explore` 为只读，无法执行验证脚本）
- QA 的核心不是“存在性检查”，而是**“接口边界交叉比对”** — 同时读取 API 响应与前端 hooks，比较 shape
- QA 不是在整体完成后跑 1 次，而是**在每个模块完成后立即增量执行**（incremental QA）
- 详细指南参见 `references/qa-agent-guide.md`

### Phase 4: 生成技能

将每个智能体所用技能生成到 `项目/.claude/skills/{name}/SKILL.md`。详细撰写指南参见 `references/skill-writing-guide.md`。

#### 4-0. 既有技能重复检讨

新建技能前，先检查 `项目/.claude/skills/` 中既有技能是否重复。反复搭建 Harness 时，功能重叠的技能容易以不同名字累积。

> 重复分类标准与一般化模式参见 `references/skill-writing-guide.md` 的“技能复用设计”。

#### 4-1. 技能结构

```
skill-name/
├── SKILL.md (必需)
│   ├── YAML frontmatter (name, description 必需)
│   └── Markdown 正文
└── Bundled Resources (可选)
    ├── scripts/    - 用于重复/确定性作业的可执行代码
    ├── references/ - 条件式加载的参考文档
    └── assets/     - 输出所使用的文件（模板、图片等）
```

#### 4-2. Description 撰写 — 主动诱导触发

description 是技能唯一的触发机制。Claude 倾向于保守地判断触发，因此 description 要写得**主动（"pushy"，急切）**。

**反例：** `"处理 PDF 文档的技能"`
**正例：** `"读取 PDF 文件、提取文本/表格、合并、拆分、旋转、加水印、加密、OCR 等所有 PDF 作业。一旦提到 .pdf 文件或请求 PDF 产物，必须使用本技能。"`

要点：同时描述技能做什么 + 具体触发场景，并写明与相似但不应触发的情形如何区分。

#### 4-3. 正文撰写原则

| 原则 | 说明 |
|------|------|
| **解释 Why** | 不用 “ALWAYS/NEVER” 这类强制指令，而是传达为什么要这样做的理由。LLM 一旦理解理由，在边缘场景也能做出正确判断。 |
| **保持 Lean（精简）** | 上下文窗口是公共资源。SKILL.md 正文目标控制在 500 行以内，不贡献分量的内容删掉或移到 references/。 |
| **一般化** | 与其写仅适配特定示例的狭义规则，不如阐明原理以覆盖多样输入。禁止过拟合。 |
| **重复代码做 bundling** | 若发现智能体们在测试执行中共同编写的脚本，提前 bundling 到 `scripts/`。 |
| **以命令式撰写** | 采用 “执行……”、“做……” 这类命令式/指示式语气。 |

#### 4-4. Progressive Disclosure（渐进式披露）

技能通过三段加载系统管理上下文：

| 阶段 | 加载时机 | 大小目标 |
|------|----------|----------|
| **Metadata** (name + description) | 始终存在于上下文 | 约 100 词 |
| **SKILL.md 正文** | 技能触发时 | <500 行 |
| **references/** | 仅在需要时 | 无限制（脚本无需加载即可执行） |

**大小管理规则：**
- SKILL.md 接近 500 行时，将细节分拆到 references/，正文中留下“何时读取该文件”的指针
- 300 行以上的 reference 文件需在顶端附**目录（ToC）**
- 若存在按领域/框架的变体，按领域拆分到 references/ 子目录，仅加载相关文件

```
cloud-deploy/
├── SKILL.md (工作流 + 选型指南)
└── references/
    ├── aws.md    ← 仅在选 AWS 时加载
    ├── gcp.md
    └── azure.md
```

#### 4-5. 技能-智能体连接原则

- 1 个智能体 ↔ 1～N 个技能（1:1 或 1:多）
- 也允许多个智能体共享同一技能
- 技能承载“怎么做”，智能体承载“谁做”

> 详细撰写模式、示例、数据 schema 标准参见 `references/skill-writing-guide.md`。

### Phase 5: 整合与编排

编排器是技能的一种特殊形态，把单个智能体与技能编织成一个工作流，统筹整支团队。如果说 Phase 4 中生成的单个技能定义“每个智能体做什么、怎么做”，那么编排器定义的就是“谁、何时、按何顺序协作”。具体模板参见 `references/orchestrator-template.md`。

**既有扩展时的编排器修改：** 当不是新建构建而是既有扩展时，不新建编排器，而是修改既有编排器。新增智能体时，将其纳入团队组成、任务分配与数据流，并在 description 中补充与新智能体相关的触发关键词。

编排器模式会根据 Phase 2-1 选择的执行模式而不同：

#### 5-0. 编排器模式（按模式）

**智能体团队模式（默认）：**
编排器通过 `TeamCreate` 组建团队，并用 `TaskCreate` 分配任务。团队成员通过 `SendMessage` 直接通信、自我协调。领导（编排器）监控进度并汇总结果。

```
[编排器/领导]
    ├── TeamCreate(team_name, members)
    ├── TaskCreate(tasks with dependencies)
    ├── 团队成员自我协调（SendMessage）
    ├── 结果收集与汇总
    └── 团队清理
```

**子智能体模式（替代）：**
编排器通过 `Agent` 工具直接调用子智能体。并行执行用 `run_in_background: true`，结果仅返回给主控。在不需要团队通信且希望降低开销时使用。

```
[编排器]
    ├── Agent(agent-1, run_in_background=true)
    ├── Agent(agent-2, run_in_background=true)
    ├── 等待并收集结果
    └── 生成整合产物
```

**混合模式：**
按 Phase 混合不同模式。常用组合：
- **并行采集（子）→ 共识整合（团队）**：Phase 2 中用子智能体并行采集独立资料 → Phase 3 中组建团队，基于讨论与共识进行整合
- **团队生成（团队）→ 验证（子）**：Phase 2 中由团队生成草案 → Phase 3 中由单一子智能体独立验证
- **Phase 间团队重组**：每个 Phase 先 `TeamDelete` 再新建 `TeamCreate`，期间插入子智能体调用

选用混合时，在编排器每个 Phase 小节顶端注明该 Phase 的执行模式（例如：`**执行模式:** 智能体团队`）。

#### 5-1. 数据传递协议

在编排器中明示智能体间的数据传递方式：

| 策略 | 方式 | 适用模式 | 适用场景 |
|------|------|----------|----------|
| **基于消息** | 通过 `SendMessage` 在团队成员间直接通信 | 团队 | 实时协调、反馈交换、轻量状态传递 |
| **基于任务** | 通过 `TaskCreate`/`TaskUpdate` 共享作业状态 | 团队 | 进度追踪、依赖管理、作业自身请求 |
| **基于文件** | 在约定路径写入并读取文件 | 团队 + 子 | 大体量数据、结构化产物、需审计追踪 |
| **基于返回值** | `Agent` 工具的返回消息 | 子 | 主控直接收集子智能体结果 |

**推荐组合（团队模式）：** 基于任务（协调）+ 基于文件（产物）+ 基于消息（实时沟通）
**推荐组合（子模式）：** 基于返回值（结果收集）+ 基于文件（大体量产物）
**混合：** 根据各 Phase 的执行模式套用相应组合

基于文件传递时的规则：
- 在作业目录下建立 `_workspace/` 文件夹保存中间产物
- 文件名约定：`{phase}_{agent}_{artifact}.{ext}`（例如：`01_analyst_requirements.md`）
- 仅最终产物输出到用户指定路径，中间文件（`_workspace/`）保留（用于事后验证与审计追踪）

#### 5-2. 错误处理

在编排器中包含错误处理方针。核心原则：失败时重试 1 次，再次失败则不带该结果继续推进（在报告中明示缺漏），冲突数据不删除而是并列出处。

> 按错误类型的策略表与实现细节参见 `references/orchestrator-template.md` 的“错误处理”。

#### 5-3. 团队规模指南

| 作业规模 | 推荐人数 | 每人任务数 |
|----------|----------|------------|
| 小规模（5～10 个任务） | 2～3 人 | 3～5 个 |
| 中规模（10～20 个任务） | 3～5 人 | 4～6 个 |
| 大规模（20 个+ 任务） | 5～7 人 | 4～5 个 |

> 成员越多，协调开销越大。3 名专注成员胜过 5 名分散成员。

#### 5-4. CLAUDE.md 中注册 Harness 指针

Harness 构建完成后，在项目的 `CLAUDE.md` 中注册最小指针。CLAUDE.md 在每个新会话加载，只记录 Harness 的存在与触发规则即可，剩余交由编排器技能处理。

**CLAUDE.md 模板：**

````markdown
## Harness: {领域名}

**目标：** {Harness 的核心目标一句话}

**触发：** 收到与 {领域} 相关的作业请求时使用 `{orchestrator-skill-name}` 技能。简单提问可直接应答。

**变更历史：**
| 日期 | 变更内容 | 对象 | 原因 |
|------|----------|------|------|
| {YYYY-MM-DD} | 初始构建 | 整体 | - |
````

**CLAUDE.md 中不放的内容：** 智能体清单、技能清单、目录结构、执行规则细节。理由：智能体/技能清单由编排器技能与 `.claude/agents/`、`.claude/skills/` 管理，属重复。目录结构可从文件系统直接确认。CLAUDE.md 仅承载**指针（触发规则）+ 变更历史**。

#### 5-5. 后续作业支持

编排器不仅要处理初次执行，也要处理后续作业。务必保证以下三点：

**1. 编排器 description 中包含后续关键词：**
仅靠首次生成关键词无法触发后续请求。description 必须包含的后续表达：
- “再次执行”、“重跑”、“更新”、“修改”、“补充”
- “只重做 {领域} 的 {子作业}”
- “基于上次结果”、“改进结果”

**2. 编排器 Phase 1 增加上下文检查步骤：**
工作流开始时确认既有产物是否存在，以决定执行模式：
- `_workspace/` 存在 + 用户请求部分修改 → **部分重跑**（仅重新调用对应智能体）
- `_workspace/` 存在 + 用户提供新输入 → **新执行**（将既有 _workspace 迁至 `_workspace_prev/`）
- `_workspace/` 不存在 → **初次执行**

**3. 智能体定义中包含再调用指引：**
在每个智能体 `.md` 文件中明示“存在上一次产物时的行为”：
- 若存在上一次结果文件，读取并反映改进点
- 若给出用户反馈，仅修改对应部分

> 参见编排器模板的 “Phase 0: 上下文检查” 小节：`references/orchestrator-template.md`

### Phase 6: 验证与测试

对所生成的 Harness 进行验证。详细测试方法论参见 `references/skill-testing-guide.md`。

#### 6-1. 结构验证

- 确认所有智能体文件位于正确位置
- 验证技能的 frontmatter（name、description）
- 确认智能体间引用的一致性
- 确认未生成命令（command）

#### 6-2. 按执行模式验证

- **智能体团队**：确认成员间通信路径、作业依赖、团队规模适当性
- **子智能体**：确认各智能体的输入输出连接、`run_in_background` 设置、返回值收集逻辑
- **混合**：确认每个 Phase 的执行模式已在编排器中明示、Phase 边界处数据传递未断（团队 → 子切换时，团队的产物是否连接到子的输入）

#### 6-3. 技能执行测试

对每个所生成的技能执行实际运行测试：

1. **撰写测试 prompt** — 为每个技能撰写 2～3 个现实测试 prompt。用真实用户可能输入的具体、自然的句子撰写。

2. **With-skill vs Without-skill 对照执行** — 尽可能并行执行有技能与无技能两种运行，确认技能的附加价值。每次派生两个智能体：
   - **With-skill**：读取技能后执行作业
   - **Without-skill (baseline，基线)**：以相同 prompt 不读技能执行

3. **结果评估** — 以定性（用户审阅）+ 定量（基于 assertion，断言）综合评估产物质量。当产物可客观验证（文件生成、数据抽取等）时定义 assertion；当主观时（文风、设计）则依赖用户反馈。

4. **反复改进循环** — 测试结果中发现问题时：
   - 把反馈**一般化**后修改技能（禁止只针对特定示例的狭义修补）
   - 修改后重新测试
   - 反复直到用户满意或不再出现有意义的改进

5. **重复模式 bundling** — 在测试执行中若发现智能体们共同编写的代码（例如：所有测试都生成相同的 helper 脚本），把该代码提前 bundling 到 `scripts/`。

#### 6-4. 触发验证

验证每个技能的 description 能否被正确触发：

1. **Should-trigger 查询**（8～10 个） — 应触发技能的多样表达（正式/口语、显式/隐式）
2. **Should-NOT-trigger 查询**（8～10 个） — 关键词相近但更适合其他工具/技能而非本技能的 "near-miss"（邻近误触）查询

**near-miss 撰写要点：** 像“写一个斐波那契函数”这种明显无关的查询没有测试价值。像“把这个 Excel 文件里的图表提取为 PNG”（xlsx 技能 vs 图像转换）这类**边界模糊的查询**才是好的测试样例。

与既有技能的触发冲突也在此阶段确认。

#### 6-5. Dry-run 测试

- 审视编排器技能各 Phase 顺序的逻辑合理性
- 确认数据传递路径中没有空缺区段（dead link，断链）
- 确认所有智能体的输入与上一 Phase 的输出相匹配
- 确认每种错误场景的回退路径可执行

#### 6-6. 撰写测试场景

- 在编排器技能中追加 `## 测试场景` 小节
- 写出 1 个正常流程 + 至少 1 个错误流程

### Phase 7: Harness 演进

Harness 不是一次造完就结束的静态产物，而是随用户反馈持续演进的系统。

#### 7-1. 执行后收集反馈

每次 Harness 执行完成后，向用户征求反馈：
- “结果中有需要改进的地方吗？”
- “智能体团队组成或工作流有想要更改的点吗？”

无反馈则跳过。不强求，但务必提供机会。

#### 7-2. 反馈反映路径

根据反馈类型，修改对象不同：

| 反馈类型 | 修改对象 | 示例 |
|----------|----------|------|
| 产物质量 | 对应智能体的技能 | “分析太流于表面” → 在技能中追加深度标准 |
| 智能体角色 | 智能体定义 `.md` | “还需要安全审查” → 新增智能体 |
| 工作流顺序 | 编排器技能 | “应先做验证” → 调整 Phase 顺序 |
| 团队组成 | 编排器 + 智能体 | “这两位似乎可以合并” → 智能体合并 |
| 触发遗漏 | 技能 description | “用这个表达就不工作” → 扩充 description |

#### 7-3. 变更历史

所有变更都记入 CLAUDE.md 的**变更历史**表（与 Phase 5-4 模板的“变更历史”小节同一张表）：

```markdown
**变更历史：**
| 日期 | 变更内容 | 对象 | 原因 |
|------|----------|------|------|
| 2026-04-05 | 初始构建 | 整体 | - |
| 2026-04-07 | 新增 QA 智能体 | agents/qa.md | 产物质量验证不足的反馈 |
| 2026-04-10 | 追加语气指南 | skills/content-creator | “过于生硬”的反馈 |
```

通过该历史可追踪 Harness 的演进方向，并防止回归（regression）。

#### 7-4. 演进触发

不仅在用户明确说“修改 Harness”时演进，下列情形也应主动建议演进：
- 同一类型的反馈反复出现 2 次以上时
- 发现智能体反复失败的模式时
- 观察到用户绕过编排器手动作业时

#### 7-5. 运维/维护工作流

系统性地对既有 Harness 进行巡检、修改与同步。Phase 0 进入“运维/维护”分支时遵循该工作流。

**Step 1: 现状审计**
- 对比 `.claude/agents/` 文件清单与编排器技能中的智能体配置 → 生成不一致清单
- 对比 `.claude/skills/` 目录清单与编排器技能中的技能配置 → 生成不一致清单
- 将审计结果向用户报告

**Step 2: 增量式新增/修改**
- 按用户请求执行智能体的新增/修改/删除，以及技能的新增/修改/删除
- 变更一次只做一项，每次变更后立即执行 Step 3（同步）

**Step 3: 更新 CLAUDE.md 变更历史**
- 在变更历史表中记录日期、变更内容、对象、原因

**Step 4: 变更验证**
- 对修改过的智能体/技能做结构验证（按 Phase 6-1 标准）
- 若修改范围影响触发，则做触发验证（按 Phase 6-4 标准）
- 大规模变更（架构变更、3 个及以上智能体新增/删除）时，执行至 Phase 6-3（执行测试）、6-5（dry-run）
- 最终确认 CLAUDE.md 与实际文件的一致性
