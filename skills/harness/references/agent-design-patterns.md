# 智能体团队设计模式

## 执行模式：智能体团队 vs 子智能体

理解两种执行模式的核心差异，并选择合适的模式。

### 智能体团队（Agent Teams）— 默认模式

团队领导者通过 `TeamCreate` 组建团队，团队成员作为独立的 Claude Code 实例运行。成员之间通过 `SendMessage` 直接通信，并通过共享任务列表（`TaskCreate` / `TaskUpdate`）自主协调。

```
[리더] ←→ [팀원A] ←→ [팀원B]
  ↕          ↕          ↕
  └──── 공유 작업 목록 ────┘
```

**核心工具：**
- `TeamCreate`：创建团队 + 派生成员
- `SendMessage({to: name})`：向特定成员发送消息
- `SendMessage({to: "all"})`：广播（成本高，慎用）
- `TaskCreate` / `TaskUpdate`：管理共享任务列表

**特征：**
- 成员之间可以直接对话、挑战、验证
- 信息交换不需要经过领导者
- 通过共享任务列表自主协调（成员可自助请求任务）
- 成员进入空闲状态时会自动通知领导者
- 可启用计划审批模式，在危险操作前先检查

**约束：**
- 每个会话同时只能**激活**一个团队（但可以在不同 Phase 之间解散旧团队并组建新团队）
- 不支持嵌套团队（成员不能创建自己的团队）
- 领导者固定（不可更换）
- 令牌成本较高

**团队重组模式：**
如果不同 Phase 需要不同的专家组合，按以下顺序操作：将上一团队的产物保存为文件 → 清理团队 → 创建新团队。上一团队的产物会保留在 `_workspace/`，新团队可通过 Read 访问。

### 子智能体（Sub-agents）— 轻量模式

主智能体通过 `Agent` 工具创建子智能体。子智能体只将工作结果返回给主智能体，彼此之间不通信。

```
[메인] → [서브A] → 결과 반환
      → [서브B] → 결과 반환
      → [서브C] → 결과 반환
```

**核心工具：**
- `Agent(prompt, subagent_type, run_in_background)`：创建子智能体

**特征：**
- 轻量快速
- 结果以摘要形式返回至主上下文
- 令牌效率高

**约束：**
- 子智能体之间不能通信
- 主智能体负责所有协调
- 无法实时协作或挑战

### 模式选择决策树

```
에이전트가 2개 이상인가?
├── Yes → 에이전트 간 통신이 필요한가?
│         ├── Yes → 에이전트 팀 (기본값)
│         │         교차 검증·발견 공유·실시간 피드백으로 품질 향상.
│         │
│         └── No → 서브 에이전트도 가능
│                  결과 전달만 필요한 생성-검증, 전문가 풀 등.
│
└── No (1개) → 서브 에이전트
              단일 에이전트는 팀 구성 불필요.
```

> **核心原则：** 智能体团队是默认模式。选择子智能体时，要自问"成员之间的通信真的不必要吗？"

## 智能体团队架构模式

### 1. 流水线（Pipeline）
串行工作流。前一个智能体的输出是后一个智能体的输入。

```
[분석] → [설계] → [구현] → [검증]
```

**适用场景：** 每个阶段强依赖于前一阶段的产物
**示例：** 小说创作 —— 世界观 → 角色 → 情节 → 撰写 → 编辑
**注意：** 瓶颈会延迟整个流水线。尽量将各阶段设计为相互独立。
**团队模式适配性：** 强顺序依赖时，团队模式的优势有限。但若流水线内存在并行区段，团队模式很有用。

### 2. 扇出/扇入（Fan-out/Fan-in）
并行处理后再合并结果。独立任务并发执行。

```
         ┌→ [전문가A] ─┐
[분배] → ├→ [전문가B] ─┼→ [통합]
         └→ [전문가C] ─┘
```

**适用场景：** 需要对同一输入从不同视角/领域进行分析
**示例：** 综合调研 —— 官方/媒体/社区/背景同时调查 → 整合报告
**注意：** 整合阶段的质量决定整体质量。
**团队模式适配性：** 这是智能体团队最自然的模式。**必须用智能体团队组建。** 成员之间可以共享发现、相互挑战，某个智能体的发现可以实时修正其他智能体的调查方向，相比单独调查质量提升显著。

### 3. 专家池（Expert Pool）
根据情境选择调用合适的专家。

```
[라우터] → { 전문가A | 전문가B | 전문가C }
```

**适用场景：** 输入类型不同，需要不同处理
**示例：** 代码审查 —— 安全/性能/架构专家中只调用相关领域
**注意：** 路由器的分类准确度是关键。
**团队模式适配性：** 子智能体更合适。只调用所需专家，无需常驻团队。

### 4. 生产者-审阅者（Producer-Reviewer）
生成智能体与审阅智能体成对工作。

```
[생성] → [검증] → (문제시) → [생성] 재실행
```

**适用场景：** 产物的质量保证重要，且存在客观验证标准
**示例：** 网络漫画 —— artist 生成 → reviewer 校验 → 重新生成问题分镜
**注意：** 必须设置最大重试次数（2~3 次）以防止无限循环。
**团队模式适配性：** 智能体团队很有用。通过 SendMessage 在生成者与审阅者之间进行实时反馈交换。

### 5. 监督者（Supervisor）
中央智能体管理工作状态，并向下级智能体动态分配任务。

```
         ┌→ [워커A]
[감독자] ─┼→ [워커B]    ← 감독자가 상태를 보고 동적 분배
         └→ [워커C]
```

**适用场景：** 工作量可变，或需在运行时决定任务分配
**示例：** 大规模代码迁移 —— 监督者分析文件列表并批量分配给工作者
**与扇出的区别：** 扇出是事先固定分配任务，监督者则观察进度动态调整
**注意：** 委派单元要足够大，避免监督者成为瓶颈。
**团队模式适配性：** 智能体团队的共享任务列表与监督者模式天然契合。通过 TaskCreate 注册任务，成员可自行领取。

### 6. 层级委派（Hierarchical Delegation）
上级智能体递归委派给下级智能体，将复杂问题逐步分解。

```
[총괄] → [팀장A] → [실무자A1]
                  → [실무자A2]
       → [팀장B] → [실무자B1]
```

**适用场景：** 问题能自然地按层次分解
**示例：** 全栈应用开发 —— 总负责 → 前端组长 → （UI/逻辑/测试）+ 后端组长 → （API/DB/测试）
**注意：** 深度超过 3 层时延迟和上下文损失都会显著增加，建议控制在 2 层以内。
**团队模式适配性：** 智能体团队不支持嵌套（成员不能再创建团队）。第一层用团队，第二层用子智能体实现，或者扁平化为单一团队。

## 复合模式

实战中，复合模式比单一模式更常见：

| 复合模式 | 构成 | 示例 |
|----------|------|------|
| **扇出 + 生产者-审阅者** | 并行生成后各自审阅 | 多语言翻译 —— 4 种语言并行翻译 → 各自由母语审阅者校验 |
| **流水线 + 扇出** | 串行阶段中部分并行化 | 分析（串行）→ 实现（并行）→ 集成测试（串行） |
| **监督者 + 专家池** | 监督者按需调用专家 | 客户问询处理 —— 监督者对问询分类后分配给合适专家 |

### 复合模式中的执行模式

**默认所有复合模式都使用智能体团队。** 成员之间的活跃沟通是结果质量的核心动力。

| 场景 | 推荐模式 | 原因 |
|---------|----------|------|
| **调研 + 分析** | 智能体团队 | 调查者之间共享发现，实时讨论冲突信息 |
| **设计 + 实现 + 验证** | 智能体团队 | 设计师 ↔ 实现者 ↔ 验证者之间的反馈环 |
| **监督者 + 工作者** | 智能体团队 | 共享任务列表实现动态分配，工作者之间共享进度 |
| **生成 + 验证** | 智能体团队 | 生成者 ↔ 验证者之间实时反馈，减少返工 |

> 仅当单一智能体需要完全隔离地执行一次性任务时，才考虑混合使用子智能体。

## 智能体类型选择

调用智能体时，通过 Agent 工具的 `subagent_type` 参数指定类型。智能体团队的成员也可以使用自定义智能体定义。

### 内置类型

| 类型 | 工具访问 | 适用场景 |
|------|----------|-----------|
| `general-purpose` | 完整（含 WebSearch、WebFetch） | 网络调研、通用任务 |
| `Explore` | 只读（无 Edit/Write） | 代码库探索、分析 |
| `Plan` | 只读（无 Edit/Write） | 架构设计、计划制定 |

### 自定义类型

在 `.claude/agents/{name}.md` 中定义的智能体，可通过 `subagent_type: "{name}"` 调用。自定义智能体可访问全部工具。

### 选择标准

| 情况 | 推荐 | 原因 |
|------|------|------|
| 角色复杂且需在多个会话中复用 | **自定义类型**（`.claude/agents/`） | 将人设与工作原则以文件形式管理 |
| 简单调研/收集，仅靠提示词即可 | **`general-purpose`** + 详细提示词 | 无需智能体文件，指令放入提示词 |
| 仅需读取代码（分析/审查） | **`Explore`** | 防止误修改文件 |
| 仅需设计/计划 | **`Plan`** | 专注于分析，避免修改代码 |
| 需要修改文件的实现工作 | **自定义类型** | 完整工具访问 + 专业指令 |

**原则：** 所有智能体都必须以 `.claude/agents/{name}.md` 文件形式定义。即使是内置类型，也要创建智能体定义文件，明确角色、原则、协议。以文件形式存在才能在下一会话中复用，且必须明确团队通信协议才能保证协作质量。

**模型：** 所有智能体使用 `model: "opus"`。调用 Agent 工具时必须显式指定 `model: "opus"` 参数。

```markdown

1. 역할1
2. 역할2
```

## 智能体拆分标准

| 标准 | 拆分 | 整合 |
|------|------|------|
| 专业性 | 领域不同则拆分 | 领域重叠则整合 |
| 并行性 | 可独立执行则拆分 | 顺序依赖则考虑整合 |
| 上下文 | 上下文负担重则拆分 | 轻量快速则整合 |
| 复用性 | 其他团队也要用则拆分 | 只在本团队用则考虑整合 |

## 智能体复用设计

创建新智能体前，检查是否与已有智能体重复。反复搭建 Harness（Harness 工具套件）容易让角色重叠的智能体以不同名字堆积。

| 情况 | 措施 |
|------|------|
| 已有智能体完全覆盖新角色 | 禁止创建新的 —— 复用已有智能体 |
| 已有智能体部分覆盖且可一般化 | 将已有智能体一般化以扩展 |
| 部分覆盖属于有意的领域特化 | 创建新的 —— 保持为独立智能体 |
| 角色范围完全不同 | 创建新的 |

**原则：** 一个智能体越聚焦于单一角色，复用性越高，重复越少。如果角色有两个以上，先看是否能拆分。

**对已有智能体进行一般化时：** 依赖该智能体的编排器、团队配置行为可能变化。扩展前确认依赖关系，一般化后通过试运行验证原有行为正常。

## 技能 vs 智能体区分

| 区分 | 技能（Skill） | 智能体（Agent） |
|------|-------------|-----------------|
| 定义 | 程序性知识 + 工具包 | 专家人设 + 行为原则 |
| 位置 | `.claude/skills/` | `.claude/agents/` |
| 触发 | 匹配用户请求关键词 | 通过 Agent 工具显式调用 |
| 规模 | 小~大（工作流） | 小（角色定义） |
| 用途 | "怎么做" | "谁来做" |

技能是智能体执行任务时参考的**程序性指南**。
智能体是利用技能的**专家角色定义**。

## 技能 ↔ 智能体连接方式

智能体使用技能有 3 种方式：

| 方式 | 实现 | 适用情况 |
|------|------|-----------|
| **Skill 工具调用** | 智能体提示词中明确写 `Skill 도구로 /skill-name 호출` | 技能是独立工作流且用户可调用 |
| **提示词内联** | 智能体定义中直接包含技能内容 | 技能简短（50 行以内）且专属本智能体 |
| **加载参考文件** | 通过 `Read` 按需加载技能的 references/ 文件 | 技能内容较大且仅在条件性需要时使用 |

建议：复用性高用 Skill 工具，专属用内联，量大用加载参考文件。
