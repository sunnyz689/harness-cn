## 1. 测试框架概览

技能品质验证是 **定性评估** 与 **定量评估** 的组合。

| 评估类型 | 方法 | 适用技能 |
|----------|------|-----------|
| **定性** | 用户直接审阅产物 | 文风、设计、创作等主观品质 |
| **定量** | 基于断言的自动评分 | 文件生成、数据提取、代码生成等可客观验证 |

核心循环：**编写 → 测试执行 → 评估 → 改进 → 重测**

## 2. 测试提示词编写方法

### 原则

测试提示词必须是 **实际用户可能输入的具体而自然的句子**。抽象或人为构造的提示词测试价值较低。

### 差例

```
"PDF를 처리하라"
"데이터를 추출하라"
"차트를 생성하라"
```

### 好例

```
"다운로드 폴더에 있는 'Q4_매출_최종_v2.xlsx'에서 C열(매출)과 D열(비용)을
사용해서 이익률(%) 열을 추가해줘. 그리고 이익률 기준으로 내림차순 정렬."
```

```
"이 PDF에서 3페이지 표를 추출해서 CSV로 변환해줘. 표 헤더가 2줄로
되어 있어서 첫 번째 줄은 카테고리, 두 번째 줄이 실제 열 이름이야."
```

### 提示词多样性

- **正式 / 随意** 语气混搭
- **显式 / 隐式** 意图混搭（直接给出文件格式 vs 需由上下文推断）
- **简单 / 复杂** 任务混搭
- 部分提示词应包含缩写、错别字、口语化表达

### 覆盖度

从 2~3 个提示词起步，但设计上需覆盖：
- 1 个核心用例
- 1 个边缘用例
- （可选）1 个复合任务

## 3. 执行测试：With-skill vs Baseline

### 3-1. 对比执行结构

对每个测试提示词**同时**派生（spawn）两个子智能体：

**With-skill 执行：**
```
프롬프트: "{테스트 프롬프트}"
스킬 경로: {스킬 경로}
출력 경로: _workspace/iteration-N/eval-{id}/with_skill/outputs/
```

**Baseline 执行：**
```
프롬프트: "{테스트 프롬프트}"  (동일)
스킬: 없음
출력 경로: _workspace/iteration-N/eval-{id}/without_skill/outputs/
```

### 3-2. Baseline 选择

| 情况 | Baseline |
|------|----------|
| 新建技能 | 不带技能执行同一提示词 |
| 改进既有技能 | 修改前的技能版本（保留快照） |

### 3-3. 时间数据采集

在子智能体完成通知中**立即**保存 `total_tokens` 和 `duration_ms`。该数据仅在通知时刻可访问，事后无法恢复。

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

## 4. 定量评估：基于断言的评分

### 4-1. 编写断言

当产物可被客观验证时，定义用于自动评分的断言。

**好断言：**
- 可客观判定为真/假
- 名称具有描述性，仅看结果就能明确其检查目标
- 验证了技能的核心价值

**差断言：**
- 与技能存在与否无关、永远通过（如 "输出存在"）
- 需要主观判断（如 "编写得不错"）

### 4-2. 可编程验证

若断言可用代码验证，则以脚本方式编写。比起肉眼查看更快、更可靠，并且可在每次迭代中复用。

### 4-3. 注意 Non-discriminating 断言

"在两种配置下 100% 通过" 的断言无法衡量技能的差异化价值。一旦发现此类断言，应予以删除或替换为更具挑战性的断言。

### 4-4. 评分结果 schema

```json
{
  "expectations": [
    {
      "text": "이익률 열이 추가됨",
      "passed": true,
      "evidence": "E열에 'profit_margin_pct' 열 확인"
    },
    {
      "text": "이익률 기준 내림차순 정렬",
      "passed": false,
      "evidence": "정렬 없이 원본 순서 유지됨"
    }
  ],
  "summary": {
    "passed": 1,
    "failed": 1,
    "total": 2,
    "pass_rate": 0.50
  }
}
```

## 5. 专家级智能体使用

在测试/评估过程中借助专家角色智能体可提升品质。

### 5-1. Grader（评分者）

执行基于断言的评分，并从产物中提取可验证的声明（claim）进行交叉验证。

**职责：**
- 对每条断言判定通过/失败 + 给出依据
- 从产物中提取事实性声明并加以验证
- 对 eval 本身的品质给出反馈（断言过于宽松或模糊时提出建议）

### 5-2. Comparator（盲测比较者）

将两份产物以 A/B 方式匿名化，在不知晓哪份是使用技能得到的结果的前提下判定品质。

**使用时机：** 希望严格确认 "新版本是否真的更优" 时。常规迭代改进中可以省略。

**评判维度：**
- 内容：准确性、完整性
- 结构：组织化、排版、易用性
- 综合分数

### 5-3. Analyzer（分析者）

分析基准数据中的统计模式：
- Non-discriminating 断言（两种配置均通过 → 缺乏区分力）
- 高方差 eval（结果在每次执行间差异大 → 不稳定）
- 时间/Token 权衡（技能虽提升品质但也提高成本）

## 6. 迭代改进循环

### 6-1. 收集反馈

向用户展示产物并接收反馈。空反馈按 "无异议" 处理。

### 6-2. 改进原则

1. **将反馈一般化** —— 仅针对测试用例的窄修是过拟合。应在原理层面进行修正。
2. **不增负重的部分一律删除** —— 阅读会话记录，若技能让智能体做了非生产性工作，则删除该部分。
3. **解释 Why** —— 即使用户的反馈很简短，也要理解其重要性并把这种理解反映到技能中。
4. **把重复工作打包** —— 若所有测试运行中都生成相同的辅助脚本，应提前放入 `scripts/`。

### 6-3. 迭代流程

```
1. 스킬 수정
2. 새 iteration-N+1/ 디렉토리에 모든 테스트 케이스 재실행
3. 사용자에게 결과 제시 (이전 iteration과 비교)
4. 피드백 수집
5. 다시 수정 → 반복
```

**结束条件：**
- 用户满意
- 反馈全部为空（所有产物无异议）
- 不再有有意义的改进

### 6-4. 草稿 → 复审模式

修改技能时，先起草再 **以全新视角重读** 并改进。不要追求一次写到位，而是经过 草稿-复审 循环。

## 7. Description 触发词验证

### 7-1. 编写触发词 Eval 查询

编写 20 个 eval 查询 —— should-trigger 10 个 + should-NOT-trigger 10 个。

**查询质量标准：**
- 实际用户可能输入的具体而自然的句子
- 包含文件路径、个人上下文、列名、公司名等具体细节
- 长度、语气、格式多样混搭
- 重点放在 **边界用例（edge case）** 而非显而易见的答案

**Should-trigger 查询（8~10 个）：**
- 同一意图的不同表达（正式 / 随意）
- 不显式说明技能/文件类型但明显需要
- 非主流使用场景
- 与其他技能竞争、但本技能应胜出的情况

**Should-NOT-trigger 查询（8~10 个）：**
- **邻近误触（Near-miss）是核心** —— 关键词相似但其他工具/技能更合适的查询
- 明显无关的查询（如 "编写斐波那契函数"）无测试价值
- 相邻领域、表述模糊、关键词重叠但上下文不同的情况

### 7-2. 既有技能冲突验证

确认新技能的 description 不会与既有技能的触发范围重叠：

1. 收集既有技能列表的 description
2. 确认新技能的 should-trigger 查询不会误触发既有技能
3. 若发现冲突，则在 description 中更明确地描述边界条件

### 7-3. 自动优化（可选高阶功能）

当需要优化 description 时：

1. 将 20 个 eval 查询按 Train(60%) / Test(40%) 划分
2. 用当前 description 测量触发准确率
3. 分析失败用例，生成改进后的 description
4. 以 Test set 为准选择最佳 description（不是 Train set —— 避免过拟合）
5. 最多迭代 5 轮

> 此流程由使用 `claude -p` 的自动化脚本执行。由于 token 成本较高，应在技能已充分稳定后再在最终阶段执行。

## 8. 工作空间结构

系统化管理测试/评估结果的目录结构：

```
{skill-name}-workspace/
├── iteration-1/
│   ├── eval-descriptive-name-1/
│   │   ├── eval_metadata.json
│   │   ├── with_skill/
│   │   │   ├── outputs/
│   │   │   ├── timing.json
│   │   │   └── grading.json
│   │   └── without_skill/
│   │       ├── outputs/
│   │       ├── timing.json
│   │       └── grading.json
│   ├── eval-descriptive-name-2/
│   │   └── ...
│   └── benchmark.json
├── iteration-2/
│   └── ...
└── evals/
    └── evals.json
```

**规则：**
- eval 目录使用 **描述性名称** 而非数字编号（例如 `eval-multi-page-table-extraction`）
- 每次迭代保存在独立目录中（不得覆盖前一次迭代）
- 不删除 `_workspace/` —— 供事后验证与审计追溯
